# CONTEXT
AcademyHub currently uses Firestore as its only database, with Firebase Auth for identity. A security review found that Firestore security rules were the sole authorization gate and contained a privilege-escalation flaw (a user could grant themselves the `admin` role by writing to their own `users/{uid}` document), plus several API routes with no server-side authorization at all.

The project is moving to Postgres as the single source of truth, accessed exclusively through server-side code (API routes / server actions), with Firebase Auth retained unchanged as the identity provider. This phase only builds the new data layer. It does not connect anything to it yet.

Target deploy region: GCP `me-central1` (Doha), via Cloud SQL for Postgres. Do not provision infrastructure in this phase — schema and migrations must simply be compatible with Cloud SQL Postgres 15+.

# OBJECTIVE
Produce a Prisma schema and an initial migration that fully and correctly models AcademyHub's current data, replacing Firestore's document/array structures with normalized relational tables — in particular giving invoices and their installments real referential integrity, which Firestore's array-in-document model could not provide.

# PROBLEM
The current data model lives in Firestore documents:
- `invoices` embed `installmentBreakdown` as an array inside the document, with no foreign key relationship to the invoice, no constraint that amounts sum correctly, and no protection against a client overwriting the whole array.
- `athletes` embed `sportsEnrolled` as an array inside the document.
- There is no relational integrity anywhere: an "installment" is just JSON, not a row that can be individually queried, indexed, or constrained.

# REQUIRED SCHEMA — MINIMUM ENTITIES
Model at least the following as real tables with foreign keys (not exhaustive — reconcile against the files above for any fields not listed here):

- **users**: `id` (uid, matches Firebase Auth UID — string PK, not auto-increment), `email`, `displayName`, `role` (enum: admin, coach, parent), timestamps.
- **athletes**: `id`, `name`, `dob`, `parentUserId` (FK → users.id — use this as the real ownership link; do not use email as a foreign key anywhere in the schema), `parentEmail` (denormalized display field only, never used for authorization), `emergencyContact`, `coppaConsent`/`coppaConsentDate` fields — rename or annotate as region-appropriate consent fields rather than hardcoding COPPA-specific naming, since the target regions are Gulf/Middle East, not US. Use a neutral name like `guardianConsent` / `guardianConsentDate`.
- **athlete_sports**: junction table for an athlete's sport enrollments (sport name, monthly fee) — replaces the `sportsEnrolled` array.
- **assessments**: `id`, `athleteId` (FK), `coachId` (FK → users.id), `sport`, `exerciseType`, `gradingRubricSop`, `dataSource` (enum: manual, ai_agentic), `pipelineStatus` (enum: deterministic_fallback, ai_evaluated, ai_error), `computedScore`, `rubricGrade`, `createdAt`. Store `quantitativeMetrics`, `qualitativeObservations`, `mediaReferences`, and `agentInsights` as JSONB columns — these are flexible/evolving nested structures and do not need full normalization in this phase.
- **invoices**: `id` (use a real UUID or Postgres-generated identifier — do not port the `INV-FAM-XXXX` random 4-digit scheme), `parentUserId` (FK → users.id, this is the authorization anchor), `parentName`, `parentEmail` (display only), `subtotal`, `discountedChildName`, `siblingDiscountAmount`, `netTotal`, `paymentSchedule`, `paymentStatus`, `issuedDate`.
- **invoice_children**: junction table linking an invoice to the athlete(s) it covers.
- **installments**: real rows, FK → invoices.id, with `label`, `amount`, `dueDate`, `status` (enum). This is the table that fixes the referential-integrity gap — add a `CHECK` constraint or application-level invariant note (in a schema comment) that installment amounts should sum to `netTotal`; a DB-level CHECK across rows isn't native Postgres, so note this as an application-layer invariant to enforce in Phase 1/2, not something to fake with a trigger in this phase.
- **schedules** and **coaches**: model minimally based on `firestore.rules` collection references and any type definitions found; flag if their shape is unclear from the current codebase rather than inventing fields.
